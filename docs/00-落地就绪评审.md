## 1. 结论（2026-09 更新）

**当前项目已经进入"可运行的 MVP 验收阶段"，不再是"尚未达到开始实现条件"。**

- 阶段一~阶段八的全部交付物均已实现并可在本机运行：工程骨架、数据库与恢复、InProcess 垂直切片、
  工具注册中心与 24 条规则、HTTP A2A、Fix/Verify/Docker 沙箱、审批与评测、Compose 与 Dashboard；
- 本文档 §3.1~§3.7 是各阶段的落地对照（P0 项**已完成**），§3.9 是"落地验收审计与 P0 修复"，
  §3.10 是逐条命令的真实执行结果，§3.11 是手工部署实测证据，§3.12 是本机环境问题（非仓库缺陷）；
- §3.9 的 P1 只保留**个人开发者范围**内的事项（SSE 接入、幂等台账归档、四容器拓扑等），
  企业级能力（K8s / Redis / Kafka / 多租户 / SSO / 公网 Agent 发现）明确不做，见宪法第十一条；
- 真实测试与 Docker 测试的执行情况、以及哪些结论只来自静态检查，全部在 §3.10/§3.11 逐条标注，
  **未在本机执行过的项目会写成 SKIP 或"未执行"，不会写成通过**。

### 3.2 与文档的有意偏离

完整裁决记录见 `docs/08-错误码与协议冻结.md` §3，摘要：

1. `review_task.input_hash` 从"全局唯一"改为"索引"，唯一性落在
   `(actor_id, command_type, idempotency_key)`——否则同一输入无法重复评测（pass@3）。
2. 子任务 `failed` 对业务命令是终态，但允许一次受控重试（attempt < 2 且错误码可重试且已对账）。
3. `NEEDS_HUMAN` 无自动出边；仅 admin 可通过 `/reviews/{id}/resume` 恢复，且永远不能进入 `MERGED`。
4. FR-010 的 LangGraph 以"显式状态机 + 持久化状态意图"实现，保留 `AgentInvoker` / `AgentHandler`
   可替换接口；Step 上限、循环检测、预算与 checkpoint 语义按 SRS §5.3 落地（**偏离项，需在验收报告说明**）。
5. 并行子任务在 PostgreSQL 上启用，SQLite 上串行降级（只影响耗时，不影响结论与安全门禁）。
6. `a2a_task` 增加 `side`（coordinator / agent）与 `remote_task_id`：MVP 允许 Coordinator 与 Agent
   服务共享同一个 PostgreSQL，两侧各自持有同一子任务的生命周期记录，Task ID 由服务端分配
   （见 docs/08 §3.7）。

### 3.5 沙箱实现取舍（与文档冲突的处理）
- docs/01 §5 要求"共享 PostgreSQL"，但 read-only 根文件系统下 Docker **不允许** `put_archive`
  写入根层，因此提交代码通过**一次性辅助容器写入命名卷**，再以只读方式挂载到沙箱的 `/src`，
  由沙箱内 `cp -R` 复制到可写 tmpfs `/work`。宿主机全程不落盘提交代码，容器与卷在 `finally` 中销毁。
- 修复配方生成的补丁**以 `os.environ["NAME"]` 失败关闭**（缺环境变量即报错），
  因此样例/黄金集的测试需自行注入环境变量；这是安全优先的取舍，已在 docs/08 记录。
- 协议模型**禁止 `str_strip_whitespace`**：补丁文本被裁剪掉结尾换行会让 `git apply` 报
  `corrupt patch`（阶段六实测发现，已在 `a2a/protocol.py` 中固化）。

## 4. 首个 Vertical Slice

第一阶段只实现不产生代码副作用的闭环：

1. `POST /api/v1/reviews` 创建父任务；
2. Coordinator 读取静态 Agent Card；
3. 通过 InProcessInvoker 创建 Review 和 Impact 子任务；
4. Review 输出 Finding，Impact 输出 ImpactReport；
5. Coordinator 校验 Artifact、更新父任务为 `REVIEWED`；
6. `GET /api/v1/reviews/{id}` 返回父任务、子任务和结果；
7. 服务重启后能从 PostgreSQL 恢复已完成和进行中的任务。

只有这个闭环通过后，才接入 HTTP A2A、Fix、Verify、Docker 和审批。这样可以先验证契约与状态机，再逐层增加副作用。

## 5. Definition of Ready

一个 Agent 在进入实现前必须提供：

- Agent Card 和输入/输出 Schema；
- 能力 allowlist 与禁止工具列表；
- Task 的超时、取消、重试和幂等行为；
- 至少一个成功样例、一个非法输入样例和一个超时样例；
- 可记录 `trace_id`、`task_id`、`parent_task_id`、`artifact_id` 和 `idempotency_key`。

## 6. Definition of Done

一个跨 Agent 功能只有同时满足以下条件才算完成：

- Schema 校验、状态迁移、权限和幂等测试通过；
- 正常、超时、重复、断线和重启场景可复现；
- 结果能在 Dashboard 和数据库中按 trace 回放；
- 失败时没有未授权文件、分支或容器副作用；
- single 和 a2a 通过同一组契约测试。

## 7. 暂不阻塞开工的事项

动态 Agent 发现、远程跨组织身份、Git 历史 RAG、向量检索增强、多 Coordinator 容灾和模型微调均属于后续路线。它们只能通过扩展已冻结的接口接入，不能反向改变 P0 状态和安全规则。
