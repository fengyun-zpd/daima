本文件是 `docs/00-落地就绪评审.md` §3 冻结项的实现记录，同时登记开发过程中发现的
文档冲突与其裁决结果。裁决顺序遵循 `CodePilot项目宪法.md` 附录：
安全底线 → 状态与审批 → A2A Schema 与幂等 → 确定性质量门禁 → 业务功能。

## 2. 新增 JSON Schema

`schemas/` 原有 4 个 Schema（Agent Card、A2A Task、ArtifactEnvelope、黄金集）。
Agent Card 声明了 `output_schemas`，但 MVP 缺少对应的负载 Schema，无法实现
FR-093"非法 Artifact 被拒绝"。因此补齐：

| 文件 | 用途 | 依据 |
|---|---|---|
| `schemas/artifact-finding-v1.schema.json` | `Finding@1.0`（FindingItem 集合） | FR-020~FR-024 |
| `schemas/artifact-impact-report-v1.schema.json` | `ImpactReport@1.0` | FR-026、FR-027 |
| `schemas/artifact-review-comment-v1.schema.json` | `ReviewComment@1.0` | SRS §5.4 |
| `schemas/artifact-patch-candidate-v1.schema.json` | `PatchCandidate@1.0` | FR-040、FR-042 |
| `schemas/artifact-patch-evidence-v1.schema.json` | `PatchEvidence@1.0` | FR-045~FR-048 |
| `schemas/artifact-verify-evidence-v1.schema.json` | `VerifyEvidence@1.0` | FR-050~FR-060 |
| `schemas/a2a-message-v1.schema.json` | `A2AMessage@1.0` | docs/05 §4 |
| `schemas/state-intent-v1.schema.json` | `StateIntent@1.0` | docs/02 §4 |

`Finding@1.0` 采用集合型 Artifact（`findings` 数组 + `stats`），一个 Review 子任务产出一个
`Finding` Artifact；单条命中为 `FindingItem`。这一取舍写在此处，避免与"每条意见一个 Artifact"
的读法冲突。

一致性由 `tests/test_schema_conformance.py` 强制：模型字段集合与 Schema `properties` 完全一致，
示例实例必须通过 `jsonschema` Draft 2020-12 校验，内容哈希篡改必须被拒绝。

## 3. 文档冲突裁决

### 3.1 `review_task.input_hash` 唯一性

- **冲突**：docs/03 §4 声明 `review_task.input_hash` 唯一；FR-002 要求"相同幂等键不创建重复任务"；
  SRS §11.3 要求同一用例独立运行 3 次统计 pass@3 / pass^3。
- **裁决**：全局唯一 `input_hash` 会让"同一输入多次运行"无法实现，违反评测要求。
  唯一性改落在 `(actor_id, command_type, idempotency_key)`（`uq_review_task_idempotency`），
  `input_hash` 建普通索引（`ix_review_task_input_hash`）用于查找。
- **实现**：`repositories/models.py::ReviewTask`，测试 `tests/test_phase2_persistence.py::test_same_input_different_key_creates_second_task`。

### 3.2 子任务 `failed` 是否终态

- **冲突**：docs/02 §5 状态图允许 `failed → working: retry_allowed`；docs/05 §6 声明
  `completed / failed / canceled` 是终态且不接受新命令；FR-095 要求"最多重试 1 次"。
- **裁决**：`failed` 对"业务命令"是终态，但允许**一次受控重试**，且必须同时满足：
  1. `attempt < 2`（Schema 中 `attempt` 上限为 2）；
  2. 失败错误码被标记为可重试（超时、沙箱超时、状态版本冲突、Agent/模型不可用）；
  3. 重试前已完成状态对账（查询 Agent 状态或命中幂等记录），即宪法第七条。
- **实现**：`domain/state_machine.py::can_retry_child`、`repositories/store.py::A2ATaskStore.transition`，
  测试 `tests/test_state_machine.py`、`tests/test_phase2_persistence.py::test_child_retry_*`。

### 3.3 `NEEDS_HUMAN` 的出边

- **冲突**：SRS §7 的状态表没有 `NEEDS_HUMAN` 行，docs/02 状态图也没有出边，但流程文档要求"转人工"，
  隐含人工处理后可以继续。
- **裁决**：自动流程中 `NEEDS_HUMAN` 没有出边（deny-by-default）。人工恢复只能通过
  `POST /api/v1/reviews/{id}/resume`，且必须：admin 角色、提供原因、携带 `expected_version`、
  目标状态在允许集合内，**永远不能是 `MERGED`**（无法绕过审批门）。
- **实现**：`domain/state_machine.py::HUMAN_RESUME_TARGETS`、`ReviewTaskStore.human_resume`，
  测试 `tests/test_state_machine.py`、`tests/test_phase2_persistence.py::test_human_resume_requires_admin_and_target`。

### 3.4 编排运行时：LangGraph 还是自研确定性编排器

- **冲突**：FR-010 要求"使用 LangGraph 实现 Coordinator 及各 Agent 的状态图"；宪法第三条只要求
  "LangGraph checkpoint 用于恢复执行，不得成为绕过数据库约束的第二状态库"。
- **裁决**：项目三以协议、状态机、权限与恢复为主线。当前实现采用**显式状态机 + 持久化状态意图**
  的确定性编排器（`agents/coordinator`、`domain/state_machine.py`、`repositories/store.py`），
  它与 LangGraph 的可观测语义一致（节点转移、checkpoint、可恢复），但不引入额外运行时依赖。
  `AgentInvoker` 与 `AgentHandler` 是保留的可替换接口，后续可在不改动协议与安全门禁的前提下
  用 LangGraph 重写单个 Agent 的内部循环。
- **影响**：这是对 FR-010 的有意偏离，须在验收报告中说明；Step 上限、循环检测、预算与
  checkpoint 语义均已按 SRS §5.3 实现。

### 3.5 并行子任务

- **冲突**：docs/01 §3 要求 Review 与 Impact 可并行；SQLite 只有单写者。
- **裁决**：PostgreSQL 上默认并行执行（`asyncio.gather` + 每子任务独立会话），
  SQLite 上退化为串行，避免锁竞争造成不确定结果。该降级只影响耗时，不影响结论与安全门禁。
- **实现**：`Coordinator.allow_parallel_children`。

### 3.6 ReviewComment 的生成方

- **冲突**：SRS §4.3 的生成层由 LLM 负责归纳；SRS §2.2 又要求 `offline` 模式不调用模型。
- **裁决**：MVP 的 `ReviewComment` 由确定性建议模板生成（`generated_by="rules"`），
  LLM 通路作为可选增强保留在 `ReviewComment.generated_by ∈ {rules, llm, rules+llm}`。
  模型不可用或 `offline` 模式下不改变 Finding 结论，只影响解释文本。
  内容守卫（`domain/llm.py::ContentGuard`）在两种生成方下都生效。

### 3.7 共享数据库下的子任务记录（`a2a_task.side` 与 `remote_task_id`）
- **冲突**：docs/01 §5 说明 MVP 单进程与多服务两种形态"共享 PostgreSQL"；
  docs/05 §3 又要求 Coordinator 与 Agent 各自持有同一子任务的状态记录，
  且 FR-096 要求 `(parent_task_id, agent_id, task_type, idempotency_key)` 唯一。
  若 Agent 侧沿用客户端传来的 `task_id` 与幂等键，两条记录会互相覆盖：
  远端任务会被误判为"已存在"，永远不会被执行（表现为状态长期停留在 `submitted`）。
- **裁决**：
  1. `a2a_task` 增加 `side ∈ {coordinator, agent}`，唯一约束改为
     `(side, parent_task_id, agent_id, task_type, idempotency_key)`；Coordinator 的默认查询
     只读 `side='coordinator'` 的行。
  2. **Task ID 由服务端分配**（A2A 语义）：Agent 服务收到提交后生成自己的 `task_id`，
     Coordinator 通过新增列 `a2a_task.remote_task_id` 关联远端任务；
     重试时使用新的幂等键（`<key>:r<attempt>`），因此远端会产生新任务，而本地跟踪行保持唯一。
  3. Artifact 归属校验接受 `本地 task_id` 或 `remote_task_id`；
     共享库部署时产物由 Agent 侧落库一次，Coordinator 只做校验与引用，避免重复入库。
- **实现**：`repositories/models.py`、`repositories/store.py`（`side` 参数与 `populate_existing`）、
  `a2a/http_invoker.py`、`apps/api/agent_service.py`；
  迁移 `migrations/versions/0003_remote_task_id.py`、`0004_task_side.py`。
- **附带修复**：跨进程调用前后必须提交本地事务并强制刷新 ORM 状态
  （`session.commit()` + `populate_existing=True`），否则协调方会基于过期快照判断重试条件。

### 3.8 补丁文本与协议序列化

- **问题**：协议模型基类曾开启 `str_strip_whitespace=True`，导致 `PatchCandidate.diff`
  的结尾换行被裁掉，沙箱内 `git apply` 报 `error: corrupt patch at line N`（阶段六实测）。
- **裁决**：协议模型**不得**做任何空白裁剪。逐字节敏感的文本字段（`diff`、`sanitized_output`）
  必须原样传输；标识符类字段改用 `pattern` / `min_length` 约束。
- **实现**：`a2a/protocol.py::ProtocolModel`，测试 `test_patch_trailing_newline_is_preserved`。

### 3.9 自动修复的失败关闭语义

- **裁决**：硬编码密钥一律改写为 `os.environ["NAME"]`（缺失即 `KeyError`），
  而不是 `os.environ.get(NAME)` 或带默认值的写法——后者会把"缺少密钥配置"变成静默的弱化行为。
- **影响**：使用该修复的项目需要在自己的测试中注入环境变量（合成黄金集已按此约定编写）；
  若测试因此失败，质量门禁会正确阻断并转人工，而不是产生"看起来通过"的补丁。
- **实现**：`agents/fix/recipes.py::_plan_hardcoded_secret`。

### 3.10 `git apply` 的尾部上下文要求

- **问题**：`git apply` 默认要求每个 hunk 至少带一行上下文；位于文件末尾的修改天然没有尾部
  上下文，严格模式会把合法补丁误判为 `patch does not apply`。
- **裁决**：先执行严格校验，仅在严格校验失败时退化为 `--unidiff-zero` 重试，并在结果与审计中
  记录退化模式（`apply mode: unidiff-zero`）。`--unidiff-zero` 只放宽上下文要求，被删除行仍必须
  逐字匹配，因此不会放过真正不匹配的补丁。
- **实现**：`repositories/repo_store.py::SyntheticRepo._apply_check`、
  `agents/verify/agent.py::_verify_argv`。

### 3.11 评测口径

- 期望标注必须与规则引擎的真实输出**逐条一致**（`tests/test_phase7_evals.py` 强制校验
  4 个代表性用例的 recall=1.0 且 precision=1.0），否则评测结果没有意义；
- `passed` 定义：`recall ≥ 0.8` 且 `precision ≥ 0.7` 且任务收敛 且 全部安全不变量为 0；
- 生成层默认使用确定性 provider，Token 记为 0；启用真实模型后必须与 `offline` 分开统计
  （docs/04 §4：不能混合统计）；
- 默认评测只跑到 `REVIEWED`（不触发 Fix/Verify），`with_fix=True` 时才执行完整沙箱链路，
  避免 20×3×3 次沙箱执行导致的超长评测时长。

### 3.12 A2A 子任务接口的归属（对外 API 只暴露父任务视图）

- **冲突**：SRS §8 早期草案与 `docs/03` 列过 `POST /api/v1/a2a/tasks`、`GET /api/v1/a2a/tasks/{id}`、
  `POST /api/v1/a2a/tasks/{id}/cancel` 三个对外路径；而 SRS §7 的权限矩阵与 `docs/05` §5 又把 A2A
  Task 接口定义在 `/internal/a2a/*`（仅 coordinator/admin）。两处并存会让"谁能创建子任务"无法判定。
- **裁决**：**对外 API 只暴露父任务视图**。子任务的创建 / 查询 / SSE 订阅 / 取消**只存在**于
  `/internal/a2a/*`（`docs/05` §5、`docs/03` §2.1），仅 `coordinator` 与 `admin` 可调用。
  SRS §8、`docs/03`、`docs/09`、`README.md` 中残留的 `/api/v1/a2a/*` 表述全部删除。
- **实现**：`apps/api/main.py` 已删除 `GET /api/v1/a2a/tasks/{task_id}` 与
  `POST /api/v1/a2a/tasks/{task_id}/cancel`（能力在 `/internal/a2a/tasks/{id}` 与
  `/internal/a2a/tasks/{id}/cancel` 原位保留，无功能损失）；
  `tests/test_api_contract.py` 冻结对外/内部路由清单，断言对外路由中不存在任何 `/api/v1/a2a` 前缀，
  防止再次发散。
- **理由**：拆分形态下 Coordinator 与 Agent 的调用关系是**运行时内部协议**；把它暴露成对外接口，
  等于允许任意客户端绕过父任务状态机直接驱动子 Agent，违反宪法第六条（状态机唯一入口）与
  第七条（恢复必须状态对账）。父任务视图已能回答"这次审查做了什么"。

### 3.13 Dashboard 技术选型（Ant Design → 原生 CSS）

- **冲突**：SRS §13 的技术栈写"React 18、TypeScript、Vite、Ant Design"。
- **裁决**：保留 React 18 + TypeScript + Vite（与 SRS 一致），**不引入 Ant Design**，使用原生 CSS。
- **理由**：Dashboard 是工作台而非组件密集型后台，Ant Design 会带来约 1MB 级依赖与额外的
  `ConfigProvider`/样式覆盖成本，对 6 个面板没有收益；MVP 的可验收点是"主流程能从页面走完"，
  与组件库无关。
- **代价与约束**：需要自行维护少量样式；因此新增 `scripts/web_check.py` 与
  `tests/test_dashboard_contract.py`，用**契约检查 + 真实构建**替代组件库带来的隐性约束
  （前端调用的每个路径必须存在于后端 OpenAPI、必须覆盖创建/状态/时间线/finding/影响/patch/
  verify/审批/审计/模式显示/错误展示等能力）。
- **状态**：属"有意偏离"，若后续需要组件库，可替换 `web/src/components/*` 而不影响 API 契约。

### 3.14 幂等账本（`idempotency_record`）与命令级语义

- **冲突**：`docs/03` §6 只声明"多个唯一约束"，多份文档也反复用"命中幂等键返回原结果"作为兜底，
  但**没有一张表记录"原结果"本身**；实现里部分写命令因此退化为"当前状态已变化 → 409"，
  这不是幂等，而是重复副作用被拒。
- **裁决**：新增 `idempotency_record` 幂等账本，作为**所有写命令**的统一幂等入口：
  - 唯一键 `(actor_id, command_type, aggregate_ref, idempotency_key)`；
  - 命中且 `request_hash` 相同 → **返回原响应负载**（`completed`）并附 `idempotent_replay: true`；
  - 命中但 `request_hash` 不同，或同一 `idempotency_key` 用于不同 `aggregate_ref`/命令 →
    `409 IDEMPOTENCY_CONFLICT`；
  - 命中 `in_progress` → `409 CONFLICT`（不并发放行）；
  - 命中 `failed` → 允许用同一键重试（失败没有产生副作用需保护）。
- **覆盖范围**：`review.create`、`fix.trigger`、`approval.decide`、`merge.apply`、`eval.run`、
  `review.resume`、`a2a.submit`、`a2a.cancel` 八类命令共用同一实现
  （`apps/api/idempotency.py::execute_idempotent`），任一命令都不会产生第二份补丁 / 审批 / 合并 /
  评测 / 子任务。
- **实现与验收**：`repositories/idempotency.py`、`migrations/versions/0005_idempotency_record.py`、
  `tests/test_p0_idempotency.py`（同键同请求返回原结果、同键异请求冲突、失败可重试、
  短键拒绝、账本落库断言）。

### 3.15 子任务状态迁移键必须按 `state_version` 区分（受控重试的终态一致性）

- **问题**：`InProcessInvoker._fail` 曾用固定键 `{task_id}:failed:{code}`。受控重试（attempt=2）
  再次失败时，`A2ATaskStore.transition` 把这条迁移判定为**首次失败的重放**并跳过，结果是
  "子任务永久停在 `working`，父任务已 `NEEDS_HUMAN`"，恢复扫描会一直看到未完成子任务。
  同一模式也存在于 `:completed` 与 `:working`。
- **裁决**：
  1. `working` / `completed` / `failed` 三类迁移键都追加迁移前的 `state_version`
     （与 `a2a/http_invoker.py` 既有的 `f"{row.id}:{key_suffix}"` 口径一致）；
  2. `A2ATaskStore.transition` 增加**重放保护**：命中同键审计记录时，只有当行已处于目标状态
     或已进入终态才允许当作重放；否则抛 `IDEMPOTENCY_CONFLICT`，让"键被复用到另一次迁移"
     立即暴露，而不是静默跳过。
- **实现**：`a2a/inprocess.py`、`apps/api/agent_service.py`、`repositories/store.py::A2ATaskStore.transition`。
- **验收**：`tests/test_scenario_review_flow.py::test_parent_cannot_reach_reviewed_when_one_child_fails`
  （断言 impact 子任务必须为 `failed`、`attempt=2`），以及 `tests/test_phase2_persistence.py` 的
  子任务幂等/终态保护用例。

### 3.16 工作区后像的结尾换行（diff 输入必须能生成可应用补丁）

- **问题**：`Workspace.from_diff` 重建的"后像"是按行拼回的，最后一行**没有结尾换行**。
  Fix Agent 依据该内容生成补丁后，沙箱里 `git apply --check` 会整段失败
  （`patch does not apply`，git 要求最后一行连换行状态一起匹配），于是所有 **diff 输入**的
  Fix/Verify 都走不到审批，只有 ZIP 输入能跑通。
- **裁决**：diff 重建的后像统一补齐结尾换行，与 ZIP 输入（文件本身带换行）对齐；
  工作区仍然标记 `partial=True`，分析视角不变。
- **实现**：`domain/workspace.py::Workspace.from_diff`。
- **验收**：`tests/test_scenario_fix_flow.py::test_verify_evidence_is_produced_in_real_sandbox`
  （真实 Docker 中断言 `apply_check.ok is True`）。

### 3.17 规则启用范围与评测口径（默认必须启用全部规则）

- **问题**：`examples/.codepilot.yaml` 的 `rules.enabled` 曾只列 R001/R002/R003，而规则集有 24 条、
  黄金集覆盖 24 条。3 用例冒烟评测恰好全过，20 用例全量评测 recall 只有 0.20，
  任何真实运行（API/演示/评测）都只执行 3 条规则。
- **裁决**：出厂配置 `rules.enabled: []`（空 = 全部规则）。需要子集时显式列出，并在
  `docs/00` §3.9.1 P0-9 记录其对 recall 的影响。
- **实现**：`examples/.codepilot.yaml`。
- **验收**：`tests/test_phase7_evals.py::test_shipped_config_enables_all_rules` 与
  `::test_expected_findings_match_real_review_output`（全部 20 个用例逐条对齐）。

### 3.18 质量门禁的证据解析与门禁失败的证据保留

- **问题 A**：`_parse_pytest` 在"ruff + pytest 拼接输出"上匹配 `(\d+) (passed|error…)`，
  ruff 的 `Found 2 errors.` 被读成 "2 errors"，把"测试全过"的补丁判为失败。裁决：只在
  `CODEPILOT_LINT_OK|FAIL` 标记之后解析 pytest 结果（`_pytest_section`）。
- **问题 B**：门禁失败时 `verify_evidence` 不写入父任务 summary，Dashboard 显示"尚无验证证据"，
  人工恢复无法判断失败原因。裁决：`_park(..., summary_extra=...)`，门禁失败时写入
  `verify_evidence` + `gate_failure`（失败层级）+ `patch_version`；`gate_failure.error_code`
  必须与父任务 `error_code` 一致（diff 输入没有测试 → 诚实报 `TEST_GAP`）。
- **实现**：`agents/verify/agent.py`、`agents/coordinator/coordinator.py`。
- **验收**：`tests/test_verify_output_parsing.py`（9 项）、
  `tests/test_scenario_fix_flow.py::test_verify_evidence_is_produced_in_real_sandbox`。

### 3.19 拆分形态必须注册全部四类 Agent 并能找到远端产物

- **问题**：① `build_agent_service` 只注册 review/impact handler，拆分形态下 Fix/Verify 子任务
  报 `AGENT_UNAVAILABLE: Agent handler 未注册`；② HTTP A2A 下 Agent 服务把产物写在**远端子任务 ID**
  下，Coordinator 按**本地子任务 ID** 查询，导致 `PATCH_INVALID: Fix 子任务未返回 PatchCandidate`。
- **裁决**：① 单进程 Coordinator 与 Agent 服务统一使用 `agents.default_handlers()` 作为唯一注册来源；
  ② `_artifact_envelope()` 支持 `remote_task_id` 兜底查询。
- **实现**：`agents/__init__.py`、`apps/api/agent_service.py`、`agents/coordinator/coordinator.py`。
- **验收**：`tests/test_deployment_contract.py::test_agent_service_registers_all_four_agents`；
  真实拆分栈 `python scripts/seed_demo.py --base-url http://127.0.0.1:8099` 跑到 `PENDING_APPROVAL`
  并完成审批与合并（`docs/00` §3.11）。
