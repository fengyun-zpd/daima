# 微调边界与后续路线

## 1. 项目三的明确选择

项目三以 A2A Agent 工程能力为主线，不训练或微调模型。原因是当前最需要验证的是任务拆分、协议契约、状态恢复、工具权限、沙箱和可观测性；如果同时改变模型，就无法判断收益来自协作架构还是参数变化。

项目三保留模型适配接口和评测数据格式，但不引入 LoRA、QLoRA、SFT、DPO、训练集生产或模型服务集群。LLM 只使用固定 Prompt、结构化输出和内容守卫。

## 2. 项目三应先建立的基线

1. `single` 模式完成 20 个黄金 PR 的审查、修复和验证闭环；
2. 固定规则、Prompt、模型、温度、Token 预算和沙箱参数；
3. 记录 Finding、Patch、VerifyEvidence、工具轨迹、Token、延迟和安全不变量；
4. 再切换 `a2a` 模式，使用相同输入和契约做对照实验；
5. 只有当 A2A 在质量、恢复或可观测性上有数据优势时，才把它作为项目三的核心成果。

## 3. 项目四的微调候选

项目四可以选择一个边界清晰的微调主题，例如：

| 候选方向 | 数据 | 目标指标 | 风险 |
|---|---|---|---|
| Finding 严重级别分类 | 脱敏 Finding、规则证据和人工标签 | Macro-F1、校准误差 | 标签一致性 |
| 修复建议结构化生成 | Finding、上下文和 approved patch | JSON 合法率、patch pass@k | 数据泄露和范围漂移 |
| 代码审查意见排序 | Finding、影响报告和人工排序 | NDCG、Top-k 命中率 | 偏好标签成本 |

优先选择分类或排序任务，再考虑生成式 SFT。生成任务必须以 `git apply --check`、测试通过率、scope drift 和安全不变量作为硬门槛，不能只看文本相似度。

## 4. 微调立项门槛

- 已有至少 100—300 条脱敏、去重并通过人工复核的样本；
- Prompt/RAG/结构化输出基线已记录，且存在明确误差来源；
- 训练、验证、测试集按仓库或项目隔离，防止相邻代码泄露；
- 先做小规模 LoRA/QLoRA 对照，保留未微调模型作为基线；
- 指标至少包含质量、稳定性、成本、延迟和安全不变量；
- 微调模型不能绕过 Coordinator、Tool Registry、审批门或 Docker 沙箱。

## 5. 路线关系

```text
项目三：single 基线 → A2A 协作 → 故障恢复与对照评测
项目四：误差分析 → 数据治理 → 小规模 LoRA/QLoRA → 离线评测 → 灰度接入
```

因此，项目三的简历和演示重点是“可控的多 Agent 系统如何完成代码审查闭环”；项目四再回答“针对已定位误差，微调是否带来可复现收益”。
